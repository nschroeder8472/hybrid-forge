# The live run the last nine changes were waiting on

Nine changes landed between 2026-09-09 and 2026-09-10 — the four entries under
*Next, in order*, the retention wiring, oscillation detection, per-role provider
guarantees, and a type checker — and every one of them shipped with the same
sentence attached: what this needs is a live run. This is that run, and the
first thing to say about it is that **a backlog which lands first try exercises
almost none of them**. The ceilings were derived from runs that failed. This one
did not fail, so most of what was built was never asked a question.

That is a result rather than a disappointment. What a green run can prove is
that none of the nine fires spuriously, which is the failure mode a set of
unexercised brakes is most likely to have.

## What ran

`examples/sample-project` copied out with `scripts/sample_workspace.py`, its
`SPEC.md` ingested, `forge go`. Three tickets: one ranking function, one report
that depends on it, one label cap in a second build. All four roles on `local`
(llama.cpp, qwen3.8, 32.8k context, 24.1k prompt budget).

The backlog was accidentally ingested three times, which turned one run into
three replications of it:

| | run 1 | run 2 | run 3 |
|---|---:|---:|---:|
| wall | 658s | 787s | 770s |
| steps | 40 | 40 | 40 |
| failed steps | 0 | 0 | 0 |
| attempts per ticket | 1, 1, 1 | 1, 1, 1 | 1, 1, 1 |

96 calls and 532.2k tokens across all three. Nine tickets, nine first-attempt
passes, zero failed steps, both suites green afterwards — 13 tests in the root
build and 8 in the plugin build.

## What each change did, honestly

**Reserved answering turns** (`ANSWERING_TURNS`, PR #59) — **not exercised.**
Reads per role across the three runs: executor 33, tester 19, reviewer 27, over
27 conversations. That is 2 to 6 reads per conversation against the six reading
turns the default leaves, so no role ever reached the withdrawal, and the
reserve neither helped nor cost anything. It bites at exhaustion, and nothing
here exhausted.

**Blocks first, prose never** (PR #58) — **not exercised.** Two calls hit their
output limit, both `ratify` votes on SP-001, neither a build. No executor reply
was truncated, so the new correction never had to choose a branch.

**Oscillation detection** (PR #62) — **not exercised, by construction.** It
reads the classes of failed steps, and there were none.

**`majorityRepeats`** — **not exercised.** All nine sign-offs were unanimous on
pass 1, so no second pass was paid and no majority was re-asked. Consistent with
the note in *Sign-off cost*: a pass-1 majority needs an impossibility landing on
exactly one role, and a four-file fixture does not produce one.

**The reference-example check** (PR #60) — **exercised, and it corrected the
entry that shipped it.** The ingest warning stayed silent for all three tickets
while `/forge-spec-check` reported two, because `cmd_ingest` widens the reading
scope before the check runs and `evidence.reading_scope` adds source siblings —
so a ticket writing `tests/report_test.py` gets `tests/counter_test.py` handed
to it. The silence was correct: every role then read that sibling. The ingest
half therefore fires only where no sibling test exists, which is narrower than
its own entry implied.

**The store's connections** (PR #57) — **exercised and quiet**, which is all it
can be. The dashboard served the run, every connection thread closed its own
handle, and nothing in the run touched a locked database.

**`forge prune`'s size report** (PR #61) — **exercised, on real data.** Pruning
the two older runs:

```
Removed 2 run(s) of artifacts, 102 KB freed.
Cleared 54 step detail row(s), 28 KB of detail.
Vacuumed run.db: 212 KB -> 176 KB.
```

`run.db` on disk immediately afterwards: 180,224 bytes, which is the 176 KB it
claimed. Before the checkpoint fix that line would have read `212 KB -> 212 KB`
about a file that shrank a moment later.

**`roleNeeds`** (PR #63) — **not exercised.** The fixture declares none, and
`validate` passed. What the run does show is the degradation it exists to make
non-silent: `local` is a text-only model and no ticket carried an image, so
nothing was there to be quietly dropped.

**The type checker** (PR #64) — nothing to exercise at runtime. It is a gate on
the tree, not behaviour in a run.

## What this run does not say

It does not say the reads got cheaper. That number wants the same backlog before
and after, and these changes landed together against a backlog that was never
read-starved to begin with. It does not say the convergence machinery works —
`_convergence`, the ladder and `flatCycles` were not called, for the sixth
consecutive green run. And it does not say anything about a large repository:
three tickets over four files is the floor case.

What it does say is that nine changes to the loop, six of which can only fire on
a failing run, are all quiet on a passing one.
